When a request cannot be completed, the cNGN API returns an appropriate HTTP status code alongside a JSON body containing a `status` field and a human-readable `message`. Understanding the error structure and knowing what each message means will help you build integrations that handle failures gracefully and recover quickly.

## Error envelope

All errors follow this structure:

```json
{
  "status": 400,
  "message": "Decryption failed"
}
```

There is no `data` field on error responses. The one exception is permission errors, where `status` is the boolean `false` rather than a number:

```json
{
  "status": false,
  "message": "Permission denied"
}
```

## Authentication and access errors

These errors are returned before any business logic runs. Fix them by correcting your credentials, key setup, or network configuration.

| HTTP | Message | Cause | Fix |
| --- | --- | --- | --- |
| `400` | `No token provided` | The `Authorization` header is missing from the request | Add `Authorization: Bearer <your API key>` to every request |
| `400` | `Invalid token prefix` | The key does not begin with `cngn_test` or `cngn_live` | Check that you copied the full key from the dashboard without truncation |
| `400` | `Merchant not found` | The API key is not recognised — it may have been revoked or mistyped | Regenerate the key in the dashboard and update your deployment |
| `400` | `No Test SSH Key found` / `No Live SSH Key found` | No Ed25519 public key has been uploaded for this environment | Upload your public key in the dashboard's security settings for the affected environment |
| `403` | `IP address not whitelisted` | The request arrived from an IP address not on your whitelist | Add your server's egress IP in the dashboard; include NAT gateways and load balancers |
| `403` | `Could not determine client IP address` | The source IP could not be resolved — usually a proxy misconfiguration | Verify that your proxy or load balancer is forwarding `X-Forwarded-For` correctly |
| `403` | `Permission denied` | Your merchant role does not hold the permission required by this endpoint | See [Permissions](/guides/permissions) for the permission map and how to request access |
| `404` | `Merchant not found` | The business role could not be resolved for this account | Contact cNGN support |

## Encryption errors

These errors occur when the API cannot decrypt your request body. They indicate a problem with how you are encrypting the payload.

| HTTP | Message | Cause | Fix |
| --- | --- | --- | --- |
| `400` | `Missing encryption data, key, or IV` | The request body was sent as plain JSON instead of the `{ content, iv }` encrypted format | Encrypt the body before sending; see the [Encryption guide](/guides/encryption) |
| `400` | `Decryption failed` | The body is encrypted but could not be decrypted — wrong AES key, malformed base64, or a corrupted IV | Verify you are using the correct encryption key for the environment and that your IV is freshly generated per request |

## Validation errors

Request fields are validated after the body has been decrypted. Validation failures return HTTP `400` with a `field: message` string that identifies exactly which field failed and why:

```json
{
  "status": 400,
  "message": "amount: Number must be greater than or equal to 1"
}
```

Parse the `message` string to surface the validation detail to your users or logs.

## Rate limiting

| HTTP | Message | Fix |
| --- | --- | --- |
| `429` | `Too many requests. Please try again later.` | Wait 60 seconds before retrying; see [Rate Limits](/guides/rate-limits) for the full quota and best practices |

## Service availability

| HTTP | Message | Cause |
| --- | --- | --- |
| `400` | `Service is currently unavailable. Please try again later.` | The redeem or withdrawal service has been temporarily disabled at the platform level |

This is a transient condition — your credentials and request are correct. Retry after a delay or check the cNGN status page for restoration updates.

## Business-logic errors

Endpoint-specific failures — such as insufficient balance, an invalid bank account number, an unsupported network, or a duplicate transaction reference — also return HTTP `400` with a descriptive message. Treat any unrecognised `400` message as **non-retryable without changing the request**. Sending the same request again will produce the same error.

<Tip>
  **Retry guidance:** safely retry `429` responses after the 60-second block window and `5xx` server errors with exponential backoff. However, do **not** blindly retry `400` responses on money-moving endpoints (withdrawals, redemptions, bridges). A `400` on those endpoints does not guarantee the operation did not reach a partial state. Before retrying, verify the current state of the operation using [Verify Withdrawal](/api-reference/verify-withdrawal) or [Get Transactions](/api-reference/get-transactions) to avoid accidental duplicate transfers.
</Tip>
