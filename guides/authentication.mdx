Every request to the cNGN API must carry an API key as a Bearer token. The key tells the API who you are, which environment you're targeting, and — combined with IP whitelisting — whether your server is authorised to make that call. Understanding how these three layers fit together will save you time when setting up a new integration or rotating credentials.

## Bearer token

Include your API key in the `Authorization` header of every request:

```bash
Authorization: Bearer cngn_live_xxxxxxxxxxxxx
```

The key prefix determines the environment. Both test and live environments share the same base URL (`https://api.cngn.co/v1/api`), so the prefix is the only thing that separates sandbox traffic from production traffic.

## Environments

<Note>
  A key from one environment will never authenticate requests in the other. Using a `cngn_test` key on a production integration — or vice versa — fails immediately with `Invalid token prefix`.
</Note>

| Environment | Key prefix | Behaviour |
| --- | --- | --- |
| **Test** | `cngn_test` | Sandbox data; safe for integration testing and development |
| **Live** | `cngn_live` | Production; real funds and real bank settlement |

Each environment carries its own independent set of credentials. You will need all three for a working integration:

| Credential | Purpose |
| --- | --- |
| **API key** | Identifies your business and selects the environment |
| **Encryption key** | AES key used to encrypt outgoing request bodies |
| **Ed25519 SSH public key** | Uploaded to the dashboard so the API can encrypt responses back to you |

Generate and manage these credentials from the **merchant dashboard** under your environment's security settings.

## IP whitelisting

After validating your API key, the cNGN API checks the source IP of the request against your whitelist. If the IP is not on the list, the request is rejected before any business logic runs:

```json
{
  "status": 403,
  "message": "IP address not whitelisted"
}
```

You manage the whitelist from your merchant dashboard. Make sure you add **every egress IP your infrastructure uses** — this includes load balancers, NAT gateways, serverless function egress ranges, and any other outbound addresses your deployment may use. A missing egress IP is one of the most common causes of unexpected 403 errors in production.

## Authentication errors

The table below covers every error the authentication layer can return, what causes it, and how to fix it.

| HTTP | Message | Cause | Fix |
| --- | --- | --- | --- |
| `400` | `No token provided` | `Authorization` header is missing entirely | Add `Authorization: Bearer <your key>` to every request |
| `400` | `Invalid token prefix` | Key does not start with `cngn_test` or `cngn_live` | Check that you copied the full key from the dashboard |
| `400` | `Merchant not found` | Key is not recognised — revoked or mistyped | Regenerate the key in the dashboard and update your deployment |
| `400` | `No Test SSH Key found` / `No Live SSH Key found` | No Ed25519 public key has been uploaded for this environment | Upload your public key in the dashboard's security settings |
| `403` | `IP address not whitelisted` | Request came from an IP not on your whitelist | Add the server's egress IP in the dashboard |

## Key rotation and safety

<Tip>
  - Store API keys and encryption keys in a **secrets manager** (AWS Secrets Manager, HashiCorp Vault, or equivalent). Never commit them to source control or expose them in client-side bundles.
  - **Rotate immediately** if you suspect a key has been exposed: generate a new key in the dashboard, update your deployment, then revoke the old key.
  - **Use test keys everywhere outside production infrastructure.** Development machines, CI pipelines, and staging environments should always use `cngn_test` keys, never `cngn_live`.
</Tip>
