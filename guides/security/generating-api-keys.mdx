The cNGN merchant dashboard issues two types of keys for each environment: an **API key** that authenticates every request as a Bearer token, and an **Encryption key** that you use to AES-256-CBC encrypt all outbound request bodies. Both keys are auto-generated by the platform — you reveal and copy them from the dashboard. Each environment — test and live — has its own completely independent set of credentials.

<Warning>
  The API key and Encryption key are each shown **only once**. Once you navigate away from the page, they cannot be retrieved again. Copy both values to a secrets manager before leaving the dashboard.
</Warning>

## Key types and environments

cNGN issues credentials in two environments so you can develop and test without touching real funds.

| Environment | Key prefix | Use case |
|---|---|---|
| **Test** | `cngn_test...` | Sandbox — no real funds moved |
| **Live** | `cngn_live...` | Production — real transactions |

Each environment holds its own API key and Encryption key. Test keys never work against live data, and live keys cannot be used in the sandbox. Keep the two sets completely separate in your infrastructure.

## Retrieving your keys

<Steps>
  <Step title="Log in to the merchant dashboard">
    Open your browser and go to [cngn.co](https://cngn.co). Sign in with your registered merchant account credentials. If you have not yet created an account, complete merchant registration first.
  </Step>

  <Step title="Navigate to Settings → API Key tab">
    From the sidebar navigation, click **Settings** and then select the **API Key** tab at the top of the settings page. This tab displays your API key and Encryption key for both environments, as well as the SSH public key field.
  </Step>

  <Step title="Reveal and copy your keys">
    Your API key and Encryption key are already generated and displayed on this tab:

    - Click the **eye icon** next to a key to reveal its value
    - Click the **clipboard icon** to copy it

    The dashboard shows two values:

    - **API key** — begins with `cngn_test_` or `cngn_live_` depending on the environment
    - **Encryption key** — a separate secret used to encrypt your request payloads

    <Note>
      Each environment has its own key set. Make sure you are viewing the environment you intend to integrate. See [Authentication](/guides/authentication#environments).
    </Note>
  </Step>

  <Step title="Store keys in a secrets manager">
    Paste the copied values into a dedicated secrets manager such as AWS Secrets Manager, HashiCorp Vault, or Doppler. Reference them in your application via environment variables at runtime.

    ```bash
    # Example: loading secrets from environment variables at runtime
    CNGN_API_KEY=cngn_test_xxxxxxxxxxxx
    CNGN_ENCRYPTION_KEY=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
    ```

    Never hard-code keys in source files, and never commit `.env` files containing live credentials to version control.
  </Step>

  <Step title="Add your SSH public key">
    On the same API Key tab, paste your **SSH public key** into the designated field. The platform uses it to encrypt response data back to you — without it, requests fail with `No Test SSH Key found` or `No Live SSH Key found`.

    Don't have a key pair yet? Create one first:

    <Card title="Generating SSH Keys" icon="terminal" href="/guides/security/generating-ssh-keys" horizontal>
      Generate an Ed25519 key pair and upload your public key to the dashboard for response decryption.
    </Card>
  </Step>
</Steps>

## What each key does

| Key | Purpose | Where it's used |
|---|---|---|
| API key | Authenticates every request | `Authorization: Bearer <key>` header |
| Encryption key | Encrypts request bodies (AES-256-CBC) | Your server, before sending `POST`/`PUT` bodies |
| SSH public key | Lets the platform encrypt responses to you | Uploaded to the dashboard API Key tab |

## Key rotation

If you believe a key has been exposed — for example, it appeared in a log, a pull request, or a chat message — contact support to regenerate it immediately. Update your secrets manager with the new value and redeploy any services that reference it.

<Tip>
  Rotate your live keys any time a team member with access to your secrets manager leaves the organisation, even if there is no evidence of misuse.
</Tip>
